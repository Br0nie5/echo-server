# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Echo (repo name "echo-server") is a self-hosted log-viewing app: a Fastify backend that watches a directory of `.jsonl` log files and serves them through a REST API, and a React frontend that displays/filters them. Optional cookie/JWT authentication and an optional cron job that pushes problem logs to Telegram.

npm workspaces monorepo with three packages:

- `echo_backend` — Fastify API server (TypeScript, ESM, Node)
- `echo_frontend` — React 19 + MUI + TanStack Query app, served by the backend under `/app` in production, by Vite in dev
- `echo_utilities` — `@echo/utilities`, a shared package (built to `dist`) consumed by both backend and frontend for types, env parsing, and log-filtering logic that must stay identical client/server-side

## Commands

Run from the repo root unless noted. Per-workspace commands can be targeted with `--workspace=echo_backend` / `echo_frontend` / `echo_utilities`.

```bash
npm run dev              # builds utilities, then runs it (tsc --watch) + backend (tsx watch) + frontend (vite) concurrently
npm run build             # runs `npm install` first (prebuild: node_modules is shared between macOS and the Linux dev container, whose platform packages differ), then builds all three workspaces, utilities first, then type-checks the root files (tsconfig.json)
npm run lint               # eslint --fix across all workspaces, then on the root files (eslint.config.js)
npm run format              # prettier --write across all workspaces and the root files, with the one root prettier.config.js
npm run arch:check           # dependency-cruiser rules, in every workspace
npm run test:coverage        # vitest run --coverage (100% threshold) across all workspaces
npm run open:coverage         # open each workspace's coverage/index.html
npm run dead-code:check        # knip: unused files, exports and dependencies, all workspaces at once (knip.json)
```

Single test file / watch mode (run inside the relevant workspace dir, e.g. `cd echo_backend`):

```bash
npx vitest run src/modules/auth/application/__tests__/signUpFirstAdmin.test.ts
npm run test:watch
```

Docker:

```bash
npm run start:docker     # builds the workspaces and the `echo:dev` image, asks which deployment of examples/ to run with it (or `-- <example>`), on ./test_logs, ./self_reports and ./data
npm run dns:enable         # makes testing.cc and local.testing.cc, the hosts of the examples, resolve to this machine (/etc/hosts, sudo); dns:disable undoes it
npm run certs:generate      # creates the self-signed testing.cc certificate of ./certs again, which the examples mount
npm run deploy:server      # multi-arch build & push to ghcr.io/br0nie5/echo:<tag>, any tag but `latest` (a version is refused when already published, any other tag is replaced), and :latest for the highest stable version
```

`examples/` holds one deployment per directory (`compose.yaml`, and the `Caddyfile` of its reverse proxy when it has one): `no-proxy-http`, `proxy-http`, `proxy-https`, `proxy-https-server-https`, `proxy-https-subdomain` and `proxy-https-base-path`. The header of each `compose.yaml` gives its address (`# URL: …`), which `scripts/start_docker.sh` prints, and its image is `ECHO_IMAGE`, the published one by default.

The image runs as the unprivileged `node` user. In it, `HTTP_PORT`, `LOGS_DIR_PATH` and `SELF_REPORTS_DIR_PATH` default to `4000`, `/watched_logs` and `/self_reports` (`ENV` of the Dockerfile, which creates these directories, the second owned by `node`, so a new named volume mounted there is writable). Its health check, `docker-health-check.ts` at the root, is run by Node.js without a build (type stripping, so erasable syntax only). The root `tsconfig.json` and `eslint.config.js` cover the files at the root only, each workspace keeping its own; `prettier.config.js`, the root `.gitignore` and `.prettierignore` apply to every workspace.

`lefthook.yml` (lefthook is a root dev dependency) runs `format` then `lint` (all workspaces) as a pre-commit hook. It runs neither the build, the tests nor `arch:check`: run `npm run build`, `npm run test:coverage` and `npm run arch:check` yourself before committing.

## Architecture

### Type flow: zod schema → shared type and route schema

The types the API exchanges are **not** hand-written, and no file is generated. Each one is a zod schema in `echo_utilities`, its single source of truth: `LogSchema`, `LogLevelSchema` and `GetLogsParamsSchema` (the query of `GET /logs`) in `src/modules/logs/schemas/`, `AuthStatusSchema` (the answer of `GET /auth/status`), `LoginRequestSchema` and `SignUpRequestSchema` in `src/modules/auth/schemas/`, `EchoErrorSchema` in `src/shared/schemas/`.

1. The type is inferred from the schema (`z.infer`), never redeclared. What a TypeScript type cannot say goes in the zod schema: `z.int()`, `.meta({ format: 'date-time' })`.
2. In `echo_backend`, a `*.schemas.ts` file converts the zod schemas to the JSON schemas the routes use with `z.toJSONSchema`, when the server starts: `presentation/logs.schemas.ts`, `presentation/auth.schemas.ts` and `shared/schemas/errors.schemas.ts`. To expose another zod schema, add it to the registry of one of them.

`echo_utilities/src/index.ts` is the single barrel export — both backend and frontend import everything from `@echo/utilities`, never by reaching into its internal paths.

### Module layout convention (backend and frontend)

Both `echo_backend/src/modules` and `echo_frontend/src/modules` are split by domain (`auth`, `logs`, and `notifications` and `selfReports` on the backend only).

The backend modules are split into layer folders, with imports only going `presentation → application → domain ← infra` (enforced by `npm run arch:check`). A module keeps only the layers it needs, and every one of its files is in one of them: a folder that is not a layer would escape the layer rules, so the check refuses it (`backend-module-files-in-a-layer`). Neither `domain/` nor `application/` imports a built-in module of Node.js or Fastify (`backend-domain-and-application-not-to-node`, `backend-domain-and-application-not-to-fastify`). Directly under `src/`, there is only `main.ts` and `server.ts`: anything else is in `modules/`, `initializers/`, `shared/` or `test/` (`backend-src-files-in-known-places`). In the core of the `logs` module, which has the four of them:

- `domain/` — the contracts the module needs from the outside: `logs.repository.ts`, the `LogsRepository`, which reads the logs of every location it watches (`getAllLogs`). A location is an opaque string saying where some logs are stored, which only the implementation gives a meaning to (a file path, the address of another server). Reading gives the logs only: a stored entry that holds no valid log is left out, and reporting it is up to the implementation; the models (`Log`, `LogLevel`) are imported from `@echo/utilities`. A `Log` carries its `location` and its `locationName`, the short name shown to the user
- `application/` — the business rules, one file per use case, named after it (`getFilteredLogs.ts`, which reads the logs of the one `LogsRepository` it is given, whatever they are made of), which know nothing of HTTP
- `infra/` — `logs.repository.ts` (`createLogsRepository`) creates the one `LogsRepository` the backend reads its logs from: the logs of the log files (`logsFiles.repository.ts`) and, when it is given a `SelfReportRepository`, the self reports too, each as a log (`logsSelfReports.repository.ts`), the files read first so the self reports saved while reading them are among the logs; `*.api.ts` reads a data source, `dto/*.dto.ts` describes what it returns (with the function converting it to a model next to it), `*.repository.ts` implements a `domain/` contract with both
- `presentation/` — `*.routes.ts`, `*.controller.ts` (the request handlers, calling into `application/`), `utils/` (pure helpers, such as the validation of the input of the handlers), and `*.schemas.ts`, the JSON schemas of the routes, derived from the zod schemas of `@echo/utilities`

`GetLogsParamsSchema` describes the query as the client sends it; `safeParseGetLogsParams` (`presentation/utils/`) validates it and turns it into what `getFilteredLogs` needs (`fromDate` and the optional `toDate` as `Date`s, `logLevels` always an array).

`logs/modules/logsNotifier/` is the submodule of `logs`, layered the same way, with the four layers. It is the optional cron that notifies the problem logs: `domain/` holds the `UnNotifiedLogsRepository` contract, which gives the logs that were not notified yet, whatever their level (`getUnNotifiedLogs`), with the function marking them as notified (`markAsNotified`), and says nothing of how what was notified is remembered; `application/checkWatchedLogsAndNotify.ts` is the use case: it keeps the unnotified logs whose level is watched (`filterLogByLevels` of `@echo/utilities`), from the newest to the oldest, notifies them and marks every log it was given as notified, unless notifying throws, so the next check notifies them again (it is also given a `SelfReportRepository` of its own, missing when the self reports are disabled), with `application/utils/buildNotifierMessage.ts` writing the message it notifies, never longer than the size limit the use case asks the `NotificationsService` for (it returns `undefined` when nothing fits, in which case nothing is sent and the use case saves a warning to its own `SelfReportRepository`, when it has one, stored in `logsNotifier.jsonl`); `infra/` holds `unNotifiedLogsCheckDate.repository.ts` (`createUnNotifiedLogsCheckDateRepository`), implementing the contract on top of the same `LogsRepository` as the routes and of the date of the last check: a read gives the logs from the date of the previous check to its own, the latter left out, so each log is given once, and every log while no date is saved (the very first check, or a last-check file that cannot be read), and `markAsNotified` saves the date of its read; the self reports, when they are among the logs of the repository, are notified like any other log: an entry that holds no valid log is stored once, with the date it was first read at, so it is notified once; `CheckDateApi` (`checkDateFile.api.ts`, the last-check file) and `dto/lastCheckDate.dto.ts` are what that date is stored with; `presentation/logs.notifier.ts` is the Fastify plugin scheduling the use case. A cron is the entry point of the submodule the way a route is the one of `logs`, hence `presentation/`. It notifies through the `NotificationsService` of the `notifications` module, which it imports the `domain/` of.

`echo_backend/src/initializers/` holds what `buildServer` registers on the Fastify app, one `register*` function per file: `registerSecurity` (cookie/JWT and CORS), `registerDocumentation` (Swagger), `registerAuthRoutes` and `registerLogsRoutes` (the routes of the API, under `apiRoutePrefix`), `registerFrontend` (the static files, under `appRoutePrefix`, and the 404 handler) and `registerLogsNotifier` (the cron), with `utils/` holding what `server.ts` shares with them or uses on its own (`normalizeToEchoError.ts`, `isOriginAllowed.ts`, `removeBasePath.ts` and `addBasePath.ts`, the `rewriteUrl` and the `Location` of the redirections of the Fastify app). They are part of the composition root, so they import the `infra/` and `presentation/` of the modules, never their `application/` (`backend-initializers-not-to-application`), and nothing but `server.ts` imports them, as nothing but `main.ts` imports `server.ts` (`backend-initializers-only-from-server`, `backend-server-only-from-entry-point`). Next to them, `settings/` holds the `Settings` the server is built from (`settings.ts`), `loadSettings.ts`, which builds them, and the parser of each variable in its `utils/` (see Environment configuration). The `register*` functions have no test of their own: `src/__tests__/server.test.ts` is the unit test of the server itself, built through them, with the routes and the cron of the modules mocked (its paths, its documentation, its frontend, CORS, the proxies, TLS, and `startServer`, whose `listen` is a stub, so no test opens a port), while their `utils/`, `loadSettings` and the `utils/` of `settings/` have unit tests (only `main.ts` is excluded from the coverage). `buildServer` takes an optional third argument, `hasLogger`, which the tests set to `false`.

A module or a submodule may import the `domain/` and the `infra/` of any other one, whether it is another module, its parent, one of its submodules or a submodule next to it, and only its `infra/` may import the `infra/` of another one; the `application/` and the `presentation/` of a module or a submodule stay its own. See `backend-modules-isolated`, `backend-parent-not-to-submodule-internals`, `backend-submodules-isolated` and `backend-submodule-not-to-parent-internals` in `.dependency-cruiser.mts`.

The backend `selfReports` module is how the backend reports its own diagnostics. It has `domain/` and `infra/` only (it has no route and no business rule of its own): `domain/` holds the `SelfReport` model (`date`, `message`, `level` (`'WARNING'` or `'ERROR'`), and `origin`, what the diagnostic is about, never empty, written `path:line:column`, `path:line` when it points to no column and `path` when it points to no line either; it has no id: two self reports with the same `level`, `message` and `origin` are the same problem), which is not derived from `Log`, the `SelfReportsSession` (what a storage knows about a self report it holds: its `sessionId`, the run of the backend it was reported during, its `location`, its `locationName` and its optional `groupName`) and the `SelfReportRepository` contract the other parts of the backend report through (`saveSelfReports`, given plain `SelfReport`s, which the repository stores with its own session) and read the self reports of every location and of every session back from (`getAllSelfReports`, each one a `SelfReport` with its `SelfReportsSession`); `infra/` holds `selfReportFiles.repository.ts` (`createSelfReportFilesRepository`, see below: the contract on top of the self-report files: a self report is a line of a file of `SELF_REPORTS_DIR_PATH/<SERVER_NAME>/`; it leaves out the self reports older than the retention when it is created, and stores a self report after the stored ones, unless one of them has its `level`, `message` and `origin`: a problem is stored once, as it was first reported), `selfReportsFiles.api.ts` (lists the self-report files, gives the path of one from the root of the file system, reads the lines of one and replaces them, through the `FilesService`), `dto/selfReportLine.dto.ts` (what a line holds, `sessionId`, `date`, `level`, `message` and `origin`, with the functions converting it to a `SelfReport` and back), `sessionIdFile.api.ts` (the `SessionIdApi`, a session file, remembering the id of the last session the self reports of one self-report file were written during: a repository has its own, and takes the next id when it is created) and `dto/sessionId.dto.ts`. It knows nothing of the logs: it imports nothing of `logs`, and a self report becomes a log in `logs/infra` only (`logsSelfReports.repository.ts`), when `INCLUDE_SELF_REPORTS_IN_LOGS` is `true` (its job is its `sessionId`, and its group the `groupName` it already carries, which `selfReportFiles.repository.ts` makes of every directory of its file, from the root of the file system: `self_reports_<SERVER_NAME>` in the container, where `SELF_REPORTS_DIR_PATH` is `/self_reports`). It logs what it cannot store or read to the `Logger` of `shared/types/logger.ts`, not to a Fastify type. A repository is created for one file, by `createSelfReportFilesRepository` (`infra/selfReportFiles.repository.ts`, given the `FilesService`, a `Logger` and plain values: the self-reports directory, the extension of its files, the name of its own file, the path of its session file and the retention), which makes its path from the self-reports directory and that file name, and gives none (`undefined`) when its storage could not be set up. It is not created at all when the self reports are disabled: `server.ts` and `registerLogsNotifier` only call it when their `SelfReportsSettings` are there (`parseLogsSelfReports` for the first, `logsNotifierSelfReports` for the second). Whoever needs to report is given its own `SelfReportRepository`, or none when the self reports are disabled, and never names a file. `logs` depends on `selfReports` through its contracts only: it imports its `domain/`, to say what it reports and to read the self reports back.

The backend `notifications` module is how the backend sends a message to the outside. It has `domain/` and `infra/` only: `domain/notifications.service.ts` holds the `NotificationsService` contract, which gives the size limit of its messages (`getMessageSizeLimit`) and sends one (`notify`, throwing when it fails), and knows nothing of what the messages say nor of the channel they go through; `infra/notificationsTelegram.service.ts` (`createNotificationsTelegramService`) implements it through the Telegram bot API, given the chat, the token of the bot, the base URL of the API and the size limit as named values. `registerLogsNotifier` builds it from the `NotificationSettings`, only when the notifications are configured, and hands it to the logs notifier, which only imports the contract.

The backend `auth` module has the four layers:

- `domain/auth.repository.ts` — the `AuthRepository` contract, the storage of the accounts: whether one exists (`hasAnyUser`), the creation of one (`createUser`, given a `NewUser`), the check of credentials (`areCredentialsValid`); `domain/signUpRefusedError.ts` — the `SignUpRefusedError` a refused sign up throws
- `application/` — `signUpFirstAdmin.ts` (`canSignUp` tells whether a user can still sign up, which the handler of the auth status asks too; `createSignUpFirstAdmin` builds the use case: only the very first user can sign up, and becomes the admin; it throws the `SignUpRefusedError` of `domain/` when another sign up is in progress or when an account already exists, the first checked and marked before any `await`, so two requests sent at the same time never both sign up, however long the storage takes to answer) and `validateCredentials.ts` (whether the credentials are those of an account, which the login handler asks)
- `infra/` — `users.db.ts` (`createUsersDb`) opens the SQLite database, `dto/user.dto.ts` describes a row of its `users` table, `authUsersDb.repository.ts` implements the contract by querying that database, hashing the passwords with bcrypt
- `presentation/` — `auth.routes.ts`, `auth.controller.ts` (the request handlers, calling the use cases, signing the JWT and setting the session cookie: the sign up, the login and the logout answer a 204 with no body, a `SignUpRefusedError` a 403 and credentials that are not those of an account a 401, both an `EchoError`; `getStatus`, the handler of `GET /auth/status`, always answers a 200 with an `AuthStatus`: `needsSignUp` while no account exists, whatever the request carries, then `authenticated` or `unauthenticated` depending on its JWT), `auth.schemas.ts` (the JSON schemas of the routes, derived from the zod schemas of `@echo/utilities`) and `auth.hooks.ts`, `rejectUnauthenticatedRequest`, answering a 401 to the requests without a valid JWT. The sign up and the login are rate limited (`credentialsAttemptsLimit` of the `AuthConfig`, 5 attempts a minute per address, `@fastify/rate-limit` registered by `registerAuthRoutes` for these routes only), and checking the credentials of an unknown user compares the password to a dummy bcrypt hash, so the time of the answer does not tell which usernames exist. No other module imports it: `initializers/registerLogsRoutes.ts` hands it to the routes to protect as their `authenticate` option (`logsRoutes`), which runs it as their `onRequest` hook, before their query is validated, only when authentication is enabled

The frontend modules are layered like the backend ones, `domain/` at the center: `presentation/` imports `application/`, and any layer may import `domain/`, which imports none of them and no package, only the models of `@echo/utilities` (enforced by `npm run arch:check`). There is no injection: `application/` imports the hook or the function of `infra/` directly, as TanStack Query makes it easy, where the backend goes through the contract of `domain/`, so the frontend `domain/` contracts mostly document what `infra/` gives. Only `presentation/` imports MUI or React Router (`frontend-ui-packages-only-in-presentation`), and every file of a module is in one of its four layers (`frontend-module-files-in-a-layer`).

The frontend `logs` module:

- `domain/` — the contract the module needs from the outside: `logs.repository.ts`, the `LogsRepository`, which fetches the logs (`findLogs`) and gives those matching the level and search filters, wherever they are filtered (`filterLogs`); the models (`Log`, `LogLevel`) are imported from `@echo/utilities`
- `infra/` — `useLogsRepository.ts`, the hook giving the `LogsRepository`: `findLogs` on top of the logs endpoint of the backend (it sends the request through `useSendApiRequest` and validates the answer against `LogArraySchema`), `filterLogs` on top of the Web Worker of `workers/`. The worker is one way to implement `filterLogs`, which filtering on the main thread or through the API would be others. In `workers/`: `filterWorkerMessages.ts` types the messages both sides exchange, `filterLogs.ts` wraps the worker into a promise-returning function (one request at a time, the logs sent only when they change, indexes sent back so the logs keep their identity, a rejection when the request is aborted, already when it is given, or the worker fails), `createFilterWorkerRequestHandler.ts` is what the worker does with a request, and `filterWorker.ts`, its entry point, is excluded from the coverage, like `main.tsx` and `src/test/`
- `application/` — the TanStack Query hooks: `useGetLogs` and `useFilteredLogs` (debounced, and cancelled when its filters change before it ends). There is no query key file: each query key is written in its hook
- `presentation/` — `LogsScreen`, plus its `hooks/`, `layouts/`, `components/` and `utils/` (the grouping of the logs by day, group and job, the log levels to offer, the `fromDate` query param)

The frontend `auth` module:

- `domain/` — the `AuthRepository` contract (`checkAuthentication`, `login`, `signUp`) and, in the same file, what it gives and throws: `AuthCheckResult` and `InvalidCredentialsError`
- `infra/useAuthRepository.ts` — the hook giving the `AuthRepository` on top of the auth endpoints of the backend: it sends the requests, validates the answer of the auth check against `AuthStatusSchema` (the login and the sign up answer no body), and turns the status of the backend into the `AuthCheckResult` of the auth check (`redirect`, `login` or `signUp`) and the 401 of a refused login into the `InvalidCredentialsError`, so that no layer above it reads an HTTP status or an axios error
- `application/` — the TanStack Query hooks: `useGetAuthCheck`, `usePostLogin` and `usePostSignUp`, the two mutations
- `presentation/` — `AuthScreen`, which shows one of two layouts after the auth check: `AuthFormLayout`, the credentials form of the login or of the sign up depending on its `formMode` (`useAuthForm` holds its state, submits with the mutation of that mode, alerts why a submit did not authenticate and redirects once it did), or `RedirectLayout`, when already authenticated, which redirects at once and shows the URL it redirects to, for the user to go there by hand in case it did not work. `hooks/useRedirectionOnAuth.ts` says where that is: the `redirect` query param only when it is a path of the app (`utils/getRedirectionPathOnAuth.ts`), since anyone can write it in a link, otherwise the logs screen

`shared/` in each workspace holds cross-module code (the config, API client setup, i18n, layouts, generic components). In the frontend it holds the contexts and what reads them (`config/ConfigContext.ts` and `useConfig`, `api/ApiContext.ts`, `useApi` and `useSendApiRequest`, the function sending a request to the API, with `isUnauthorizedError` next to it, which navigates to the auth screen on a 401 outside of it, with `useGoToAuthScreen` of `shared/navigation/`, so no request handles it on its own) and `AppPathNames`, the paths of the screens below `APP_URL`, the `basename` of the router of `AppRouter`: the app only navigates inside itself, with React Router, and imports nothing of the frontend but itself (`frontend-shared-is-self-contained`); `echo_frontend/src/initializers/` holds only what sets them up (`AppProviders`, which nests `ConfigProvider` and `ApiProvider` in the theme and the `queryClient`, and `AppRouter`, whose `buildRouteElement` prop replaces what a route displays, its screen by default), which nothing but `App.tsx` imports (`frontend-initializers-only-from-app`), as nothing but `main.tsx` imports `App.tsx` (`frontend-app-only-from-entry-point`). In the backend it also holds `types/logger.ts`, the `Logger` a part of the backend writes its errors to, and `services/`, what several modules do the same way: `files.service.ts` holds the `FilesService`, the one access of the backend's own code to the file system: nothing else imports `fs`, not even the tests, but its own (`backend-fs-only-through-files-service`); only libraries given a path by the settings reach the disk on their own (`better-sqlite3`, `dotenv`, `@fastify/static`). It creates a directory (`createDirectory`), reads a file as a whole (`getFileContent`) or as lines of text (`getFileLines`), throwing a `FileDoesNotExistError` (`shared/services/fileDoesNotExistError.ts`) when it is missing, lists files (`getFilesPaths`), gives the path of a file relative to a directory, or to the root of the file system, `undefined` when it is not below it (`getRelativeFilePath`), writes a file the same two ways, in one step, leaving no temporary file behind when it fails, one write of a file after the other, a write waiting for the previous one for 10 seconds at most (`replaceFileContent`, `replaceFileLines`), and makes a file readable by its owner only (`restrictFileAccessToOwner`). `logs/infra` catches the `FileDoesNotExistError` to read a missing log file as one with no line. It knows nothing of what the files hold nor of how they are named: `getFilesPaths` is given the function saying which files to include, so the `.jsonl` extension stays in the settings. `startServer` builds it once and hands it to `loadSettings` (the TLS certificate and key) and to `buildServer`, which gives it to whatever reads or writes files: the log files of `logs/infra`, the last-check file, the self-report files and the session files of the self reports, and the users database. Tests get a fake one from `test/mocks/mockFilesService.ts` (`getMockFilesService`). It also holds `config/`, the types of the configs the modules are given, and nothing else of the configuration (see Environment configuration). `shared/` imports nothing of the backend but itself (`backend-shared-is-self-contained`).

A relative import never leaves its package, tests included (`no-relative-import-outside-package`): what is outside is either a package imported by its name (`@echo/utilities`, only through its barrel) or a file read when the server runs, whose path is in the config.

### Environment configuration

Env vars are parsed and validated once at startup, not read ad hoc via `process.env` elsewhere in the code:

- `parseConfig` (`echo_utilities/src/shared/config/parseConfig.ts`) parses the vars common to both frontend and backend into the `Config` (`shared/config/config.ts`): `SERVER_NAME` and `HAS_AUTHENTICATION`. Next to it, `shared/config/utils/` holds what the three configs read a variable with, exported by the barrel: `requireEnv` (the text of a required variable, without the spaces around it, throwing when it is missing or blank; a number or a boolean of the JSON env of the frontend is given as its text), `addEnvNameToError` (names the variable in the error of a parser), `parseRequiredEnv` (both: a required variable, parsed by the parser it is given), `parseBoolean` and `parseInteger` (digits only, after an optional minus sign), which the parsers of a port or of a number of days build on. A parser of a single value takes its text and knows nothing of the name of its variable. Where Echo is reached is not shared, and no variable gives its URL: the backend reads the protocol and the host from each request, and only the path a reverse proxy serves it under from `BASE_PATH`, and the frontend reads it from its page (`parseAppUrls`, below). The route prefixes are `apiRoutePrefix` and `appRoutePrefix` of `echo_utilities/src/shared/config/routePrefixes.ts`.
- `echo_backend/src/initializers/settings/loadSettings.ts` builds the `Settings` (`initializers/settings/settings.ts`) from that, the backend-only vars and constants, and throws on startup if required vars are missing/invalid. A variable is required unless being unset means something (`BASE_PATH`, `TRUSTED_PROXIES`, the TLS and Telegram variables): no parser holds a default value, the ones of the container being in `docker-entrypoint.sh`. The variables of a part that is disabled are not read, so they stop nothing: `SELF_REPORTS_RETENTION_DAYS` and `SELF_REPORTS_DIR_PATH` are required only when the self reports are enabled, that is when something uses them (today, when `INCLUDE_SELF_REPORTS_IN_LOGS` is `true`), the three `LOGS_NOTIFIER_*` only when the notifications are configured. Each variable is read by its own parser, one per file in `initializers/settings/utils/` (`parseHttpPort`, `parseTlsSettings`, `parseLogsNotifierSettings`, …): what a variable gives when it is unset, invalid or set to a given value is unit-tested there, while the tests of `loadSettings` only cover which env file is loaded, that the error of a parser is thrown, and all the settings compared to the expected ones. It loads `.env.production` or `.env.development` based on `NODE_ENV`, from the working directory (`echo_backend/`, where npm runs its scripts). `NODE_ENV` only chooses that file: no variable is read differently in development. The Vite dev server in front of the backend serves the app and proxies the API over HTTP only, so the TLS variables stay unset there. `Settings` are split by what uses them: `server` (`ServerSettings`: `serverName`, `basePath` (`BASE_PATH`, the path a reverse proxy serves Echo under, empty at the root: `parseBasePath` refuses one starting like a route prefix), `apiRoutePrefix`, `appRoutePrefix` and `documentationRoutePrefix` (the paths the API, the frontend and the docs are served under, below `basePath`), `hasDocumentationRoute` (`HAS_DOCUMENTATION_ROUTE`, a required boolean read by `parseBoolean`: whether the docs are served), `host`, `port` (from `HTTP_PORT`), `trustedProxies` (`TRUSTED_PROXIES`, read by `parseTrustedProxies`: the optional list of the reverse proxies whose `X-Forwarded-*` headers are believed: IP addresses, CIDR ranges and named ranges separated by `;`, a host name being refused; missing when the variable is unset, whatever sends the request then being believed, so the server works behind any proxy without being told; given to Fastify as its `trustProxy`, `true` when it is missing), optional `tls` (`TlsSettings`), `frontendDistDirPath`), the optional `auth` (`AuthSettings`, left out unless `HAS_AUTHENTICATION` is `true`: its `config`, the `AuthConfig` (`sessionDurationSeconds`, `credentialsAttemptsLimit`, `cookieName`, `cookieSerializeOptions`), and `usersDbFilePath`), `logs` (`LogsSettings`: `logsDirPath` (`LOGS_DIR_PATH`, the one directory the logs are read from), `logFileExtension`, `logFilesDirName` (the `logs` directory scripts put their log files in, left out of the group names), and the optional `logsNotifier` (`LogsNotifierSettings`: its `config`, the `LogsNotifierConfig` (`schedule`, `watchedLogsLevels`, `timezone`, `serverName`), and `lastLogsCheckFilePath`)), the optional `parseLogsSelfReports` and `logsNotifierSelfReports` (two `SelfReportsSettings`, one per part of the backend that reports, both left out unless something uses the self reports, that is unless `INCLUDE_SELF_REPORTS_IN_LOGS`, a required boolean, is `true`: `retentionDays`, `dirPath`, the self-reports directory (`createSelfReportsDirPath`: `<SERVER_NAME>` under `SELF_REPORTS_DIR_PATH`, `SERVER_NAME` being made safe for a path) and `fileExtension`, the same in both, then `fileName` and `sessionFilePath`, the file and the session file of that part) and the optional `notification` (`NotificationSettings`: `telegramChatId`, `telegramBotToken` (from `TELEGRAM_BOT_TOKEN`), `telegramBaseUrl` (a constant, the bot API without the token), `telegramMessageSizeLimit`).
- Settings and configs are two things. The settings are everything `loadSettings` builds, and they stay in the composition root: only `server.ts` and `initializers/` read them (`initializers/` is imported by nothing else, `backend-initializers-only-from-server`). A config is the part of the settings a module is given as it is, which any of its layers may know, and only its type is in `shared/config/`: `AuthConfig` (`authConfig.ts`) and `LogsNotifierConfig` (`logsNotifierConfig.ts`). `shared/config/` holds no parser and no value. What only an implementation needs (a path, a file name, an extension, a token) is in no config, so the `presentation/` and the `application/` of a module never see it: the `infra/` that needs it asks for it as one inline object of named values (`createUsersDb({ usersDbFilePath }, filesService)`, `createLogsFilesApi({ logsDirPath, logFileExtension, logFilesDirName }, filesService)`, `createCheckDateFileApi({ lastLogsCheckFilePath }, filesService)`, `createNotificationsTelegramService({ telegramChatId, … })`), which an initializer fills from the settings. A setting that a `presentation/` or an `application/` needs goes in a config; any other one stays a plain setting.
- Paths and file names are part of the settings too (the `data/` directory and its files, the self-reports directory, the `.jsonl` extension of the log files, `parseLogFile.jsonl`): no module builds a path from `import.meta.url` or declares a file name of its own, but `loadSettings`, which builds the root of the repository from it. A value needed in two places is in both (`serverName`, in `ServerSettings` and in `LogsNotifierConfig`). `buildServer` (`server.ts`) receives the `Settings` and the `FilesService`; `startServer`, next to it, builds the `FilesService`, awaits `loadSettings` (async, as it reads the TLS files through that service), builds the server and starts listening, and `main.ts`, the entry point, only calls it. Tests get a config from `test/mocks/mockConfigs.ts`, which a unit test of a module uses alone, and settings from `test/mocks/mockSettings.ts`, for the tests on the real server.
- `echo_frontend/src/shared/config/utils/parseFrontConfig.ts` builds the `FrontConfig` (`shared/config/frontConfig.ts`), which `useConfig` gives: the `Config`, plus the frontend-only `LOGS_INITIAL_DATE_DAYS_AGO` (how many days back the logs start by default) and `LOGS_MINIMAL_DATE_DAYS_AGO` (how many days back they can start at most), each read by `parseDaysAgoNumber`, next to it, through `parseRequiredEnv`. It throws if one is missing or invalid, or if the first is greater than the second. `docker-entrypoint.sh` defaults them to `2` and `14`.
- The frontend reads where it and the API are reached (`APP_URL`, `API_URL` of the `FrontConfig`) from the `<base>` of its page, which the backend adds to `index.html` and a plugin of `vite.config.ts` in dev, the tests from the `<base>` `setupTests.ts` adds: `parseAppUrls` (`shared/config/utils/`) gives the app at the base and the API next to it, on the host the user reached.
- The frontend fetches its runtime env from a generated `env.<mode>.json` file (see `docker-entrypoint.sh`, which writes `env.production.json` from container env vars at container start — this is how the same built frontend bundle is reconfigured per deployment without rebuilding). In dev, the frontend runs on a different port than the backend (Vite on `:5173` vs the API on `:4000`), so `echo_frontend/vite.config.ts` proxies `/api` and `/documentation` to the backend — forwarding the `Host` header as it is (no `changeOrigin`), so the app and the API share one origin (`http://localhost:5173`) in development too, which the CORS check of the backend relies on.
- `HAS_AUTHENTICATION=false` disables cookie/JWT registration and the `auth` routes entirely (see `registerSecurity.ts` and `registerAuthRoutes.ts` in `echo_backend/src/initializers/`); the frontend must handle both modes.
- The optional Telegram cron (`echo_backend/src/modules/logs/modules/logsNotifier/presentation/logs.notifier.ts`) only registers if `config.logs.logsNotifier` and `config.notification` are set (the first is left out when the second is), that is if `TELEGRAM_CHAT_ID` and `TELEGRAM_BOT_TOKEN` are both present (`LOGS_NOTIFIER_SCHEDULE`, `LOGS_NOTIFIER_WATCHED_LOGS_LEVELS` and `LOGS_NOTIFIER_TIMEZONE` are then required, and a missing or invalid one stops the server at startup); it tracks last-checked time in `data/last_logs_check.json`.

### Log storage and parsing

Logs are read directly from `.jsonl` files on disk (the directory of `logsDirPath`, `LOGS_DIR_PATH`, and no other), not from a database — `infra/logsFiles.api.ts` lists the log files of that directory (the files with the `logFileExtension` it is given) and reads the lines of one, through the `FilesService` of `shared/services/`; `infra/logsFiles.repository.ts` implements the `LogsRepository` of `domain/` on top of it, a location being the path of a log file: it converts each line to a log (`convertRawLogLineToLog` in `infra/dto/rawLogLine.dto.ts`, the schema of a line being in `infra/dto/rawJsonLog.dto.ts`) and, each time the logs are read, saves a warning self report for each line that holds none to the `SelfReportRepository` it is given, all in a single save, when it is given one (its `origin` is the path of the file and the position of the line, `path:line`). A line holds neither the `id`, the `locationName` nor the `groupName` of a log: they are worked out again each time it is read. The `id` is created by `createLogId` of `@echo/utilities`, given the log without its id: it is made of an `idNumber` (here the position of the line), its `date`, its `jobId`, its `location`, `level`, `message` and `origin`. The `groupName` is created by `logsFiles.api.ts` itself, from the path of the file below the logs directory, which the `FilesService` gives it (`getRelativeFilePath`): it is made of its directories, joined with `_`, without those named like the `logFilesDirName` it is given nor the first of the others. The `origin` of a log, where the script says it was emitted from, is optional, and never an empty string. `infra/logsSelfReports.repository.ts` implements the same contract on top of a `SelfReportRepository`, and `infra/logs.repository.ts` gives both as one. `getFilteredLogs` (`application/getFilteredLogs.ts`) filters the logs of the repository and sorts them from the newest to the oldest, in memory. `filterLogByLevels` / `filterLogBySearch` (in `@echo/utilities`, shared with the frontend) implement the actual filter logic so backend filtering and frontend live-filtering (`echo_frontend/src/modules/logs/infra/workers/createFilterWorkerRequestHandler.ts`, run in a Web Worker) stay in sync.

### Auth

Backend stores users in a local SQLite file at `data/users.db` (`echo_backend/src/modules/auth/infra/users.db.ts`, `better-sqlite3`) with bcrypt-hashed passwords. JWT secret is a fresh random value generated at process start (`crypto.randomBytes` in `initializers/registerSecurity.ts`) — sessions do not survive a server restart. A session lasts `sessionDurationSeconds` of the `AuthConfig` (one day), both its cookie (`maxAge`) and its JWT (`expiresIn`, set in `registerSecurity.ts`). The JWT is delivered via an httpOnly cookie, named after `SERVER_NAME` (`createSessionCookieName` in `initializers/settings/utils/`: `<SERVER_NAME>_echo_access_token`, made safe for a cookie name), whose options are built at startup (`createCookieSerializeOptions`, next to it): it is bound to no domain, so the browser only sends it back to the host that set it, its path is the `basePath` of the `ServerSettings` (`/` when it is empty), so two instances served at two paths of one host keep their own session, and whether it is `secure` is decided for each request (`secure: 'auto'` of `@fastify/cookie`), from its protocol, since a browser refuses a secure cookie set over HTTP: HTTPS when the backend has a `tls` config, or when one of the `trustedProxies` forwards the request with `X-Forwarded-Proto: https`. While `trustedProxies` is missing, a client could name any address in `X-Forwarded-For`, so `registerAuthRoutes` counts the login and sign-up attempts per connecting address (the proxy, when there is one) and per `request.ip` only once the proxies are listed.

CORS (`registerSecurity.ts`) only allows the origin a request is itself sent to (`isOriginAllowed`, comparing the `Origin` header to `request.host`), so a reverse proxy must forward the host the browser reached, as the `Host` header or, when it is one of the `trustedProxies`, as `X-Forwarded-Host`.

### Serving frontend from backend

In production the backend serves the built frontend static files (`echo_frontend/dist`) under `/app` via `@fastify/static` (`initializers/registerFrontend.ts`), with a catch-all `notFoundHandler` returning `index.html` for any `/app/*` route (SPA routing) and a 404 `EchoError` for everything else, `/application` included. The root (`/`) is a hidden route redirecting to `/app/`, below the `basePath` like any redirection. API routes are mounted under `/api`.

Echo can be reached at any path behind a reverse proxy, `BASE_PATH` (`basePath` of the `ServerSettings`), which the proxy may forward or strip: the Fastify app is built with a `rewriteUrl` (`removeBasePath`) taking it off the requests that carry it, so the routes stay under `/api`, `/app` and `/documentation`, and an `onSend` hook puts the `Location` of a redirection to a path of the server below it (`addBasePath`), where the browser reaches it. The frontend is built with a relative base (`./`, `vite.config.ts`; the dev server and the tests keep `/app`), and `registerFrontend` never serves `index.html` as it is: it reads it through the `FilesService` and answers it with a `<base href="<basePath>/app/">`, which its assets and `env.production.json` resolve against. Swagger UI is given the `basePath` as its `indexPrefix`, and the OpenAPI document the `basePath` as its server, when there is one: a relative URL, resolved on the origin the document is loaded from.

### Swagger / OpenAPI

`@fastify/swagger` + `@fastify/swagger-ui` are registered in `initializers/registerDocumentation.ts` and serve live docs at `/documentation`, only when `hasDocumentationRoute` of the `ServerSettings` is `true` (`HAS_DOCUMENTATION_ROUTE`, required, which `docker-entrypoint.sh` defaults to `false`): otherwise neither is registered, and `/documentation` answers the 404 of any unknown path. Keep route `schema` blocks (especially `operationId`, request/response shapes) accurate, since they drive these docs.

## Documentation of a package

The README, the documentation comments and the tests of a package talk about that package only. What links the packages is said here, in the root `README.md` and in `docs/`: who imports `@echo/utilities`, that it is built before the others, that the filtering is shared so the backend and the frontend filter the same way, that the frontend reads the `AuthStatus` the backend answers its auth check with to redirect, or to show the login form or the sign up one.

## Sample data

`test_logs/` and `self_reports/`, at the root, hold real logs, git-ignored so that they stay out of the repository. Nothing that is committed takes a value from them, whether a mock, a fixture, an example of the documentation or anything else: no group, script or server name, no path, no message. Invent the data instead (`billing`, `send_invoices`, `Quota almost reached`), and do not read these directories to write it.

## Testing

Vitest is used in all three workspaces with 100% coverage thresholds enforced by `test:coverage` (see `vitest.config.ts` in the backend and the utilities, and `vite.config.ts` in the frontend, for exclude lists — the entry points are excluded). Tests live in `__tests__` directories colocated with the code under test.

`echo_utilities` only has unit tests, covering every case of each function and schema.

In `echo_backend`, a route or the cron takes the place a screen has in the frontend: each has a few integration tests on the real server (`logs.routes.test.ts`, `auth.routes.test.ts`, `logs.notifier.test.ts`). `buildTestServer` (`src/test/`) builds it with `buildServer` and settings with authentication and nothing optional, which a test completes with the part it is about. Only the outside is replaced: the file system, by `createInMemoryFileSystem` (`src/test/mocks/`), which the real `FilesService` runs on, so a test fills the files, sends requests with `server.inject` and reads the files back; the users database, an in-memory SQLite one (`:memory:`); and `fetch`, stubbed, for the notifications. The cron is only registered in its own test, where it is run by moving the fake clock a minute. A logs test signs the JWT of its session itself (`server.jwt.sign`), and the self reports are off unless a test is about them. What these tests do not reach is unit-tested where it is handled: the use cases, the `infra/` adapters and the DTOs (with `getMockFilesService`, whose methods are mocks), `shared/`, the `utils/`, and one edge case of the auth controller. The JSON schema of a route refuses an invalid request before its handler runs, with the messages of Fastify: the messages of `safeParseGetLogsParams` are only answered for what that schema lets through (a date that is not an ISO one).

In `echo_frontend`, a module is tested through its screen, with a few integration tests (about ten for the logs screen, five for the auth one, in `LogsScreen.test.tsx` and `AuthScreen.test.tsx`): a snapshot shows what the user sees (two for the logs, a wide screen and a tall one), and every other test is an action of the user, one test telling a whole feature (the level filter read from the address then changed with the chips, a day opened then closed), never one test per variant. What these do not reach is an edge case, unit-tested where it is handled (`parseDateQueryParam`, `useAuthRepository`). Two helpers of `src/test/renderApp.tsx` render the app at a path, with its real providers and router. `renderFakeRouterApp` is the one a screen test uses: only the screen of that path is real, any other one being replaced by an empty box whose test id `getRouteTestId` gives for the path the app went to (query string included), so the test of a module never renders another module nor mocks its requests, and only checks where the app navigated. `renderRealRouterApp` renders the real `App`, every screen included: it is for the snapshots, and for `App.test.tsx`. They differ by one thing, the `buildRouteElement` the fake one gives `AppRouter`. `getAppPath` tells the path the app is at. Only the network is mocked (`nock`, a request mocked but never sent failing its test), and the Web Worker, which jsdom cannot start (`stubFilterWorker` runs `createFilterWorkerRequestHandler` on the thread of the test, so the queue of `filterLogs.ts` is the real one). `App.tsx` and `initializers/` therefore have no test of their own, but the `utils/` of the initializers, and `src/__tests__/App.test.tsx` is the unit test of the app itself, its config (which cannot be loaded, or is not valid) and its routes (with and without authentication): both screens are mocked there (`vi.mock`, a box with a test id each), so a change in a screen never changes that file. `shared/`, the `utils/` folders and the edge cases of `infra/` have unit tests, a component rendered alone with `renderComponent` (the theme and the translations, nothing else) and a hook needing the config, the API or the router with `renderAppHook`. The screen tests set the date with `vi.useFakeTimers({ now, toFake: ['Date'], shouldAdvanceTime: true })`: the timers stay real, and the date goes on, which the debounce of the filters needs. A test finds a text of the app by its translation key (`appTranslation` of `src/test/utils/`). `src/test/` only holds the render functions at its top (`renderApp.tsx`, `renderAppHook.tsx`, `renderComponent.tsx`), the components they render under `components/`, what stands for the outside under `mocks/` (`mockConfig`, `mockUrl`, `stubFilterWorker`) and the small helpers of a test under `utils/`, never by the English text.
