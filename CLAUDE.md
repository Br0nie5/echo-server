# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Echo (repo name "echo-server") is a self-hosted log-viewing app: a Fastify backend that watches a directory of `.jsonl` log files and serves them through a REST API, and a React frontend that displays/filters them. Optional cookie/JWT authentication and an optional cron job that pushes problem logs to Telegram.

npm workspaces monorepo with three packages:
- `echo_backend` — Fastify API server (TypeScript, ESM, Node)
- `echo_frontend` — React 19 + MUI + TanStack Query app, served by the backend under `/app` in production, by Vite in dev
- `echo_utilities` — `@echo/utilities`, a shared package (built to `dist`) consumed by both backend and frontend for types, env parsing, and log-filtering logic that must stay identical client/server-side

## Commands

Run from the repo root unless noted. Per-workspace commands can be targeted with `--workspace=echo_backend` / `echo_frontend` / `echo_utilities`.

```bash
npm run dev              # runs backend (tsx watch) + frontend (vite) concurrently
npm run build             # builds all three workspaces (utilities must build before backend/frontend can type-check against it)
npm run lint               # eslint --fix across all workspaces
npm run format              # prettier --write across all workspaces
npm run test:coverage        # vitest run --coverage (100% threshold) across all workspaces
npm run open:coverage         # open each workspace's coverage/index.html
npm run dead-code:check        # knip: unused files, exports and dependencies, all workspaces at once (knip.json)
```

Single test file / watch mode (run inside the relevant workspace dir, e.g. `cd echo_backend`):
```bash
npx vitest run src/modules/logs/application/__tests__/getFilteredLogs.test.ts
npm run test:watch
```

Docker:
```bash
npm run build:docker    # builds workspaces, rebuilds the `echo` image
npm run start:docker     # builds + runs the container, mounting ./test_logs -> /watched_logs and ./data -> /app/data
npm run deploy:server      # multi-arch build & push to ghcr.io/br0nie5/echo:latest
```

`lefthook.yml` runs `format` then `lint` (all workspaces) as a pre-commit hook. It runs neither the build, the tests nor `arch:check`: run `npm run build`, `npm run test:coverage` and `npm run arch:check` yourself before committing.

## Architecture

### Type flow: zod schema → shared type and route schema

The types the API exchanges are **not** hand-written, and no file is generated. Each one is a zod schema in `echo_utilities`, its single source of truth: `LogSchema`, `LogCategorySchema` and `GetLogsParamsSchema` (the query of `GET /logs`) in `src/modules/logs/schemas/`, `AuthTokenSchema`, `LoginRequestSchema` and `SignUpRequestSchema` in `src/modules/auth/schemas/`, `EchoErrorSchema` in `src/shared/schemas/`.

1. The type is inferred from the schema (`z.infer`), never redeclared. What a TypeScript type cannot say goes in the zod schema: `z.int()`, `.meta({ format: 'date-time' })`.
2. In `echo_backend`, a `*.schemas.ts` file converts the zod schemas to the JSON schemas the routes use with `z.toJSONSchema`, when the server starts: `presentation/logs.schemas.ts`, `presentation/auth.schemas.ts` and `shared/schemas/errors.schemas.ts`. To expose another zod schema, add it to the registry of one of them.

`echo_utilities/src/index.ts` is the single barrel export — both backend and frontend import everything from `@echo/utilities`, never by reaching into its internal paths.

### Module layout convention (backend and frontend)

Both `echo_backend/src/modules` and `echo_frontend/src/modules` are split by domain (`auth`, `logs`, and `selfReport` on the backend only).

The backend modules are split into layer folders, with imports only going `presentation → application → domain ← infra` (enforced by `npm run arch:check`). A module keeps only the layers it needs, and every one of its files is in one of them: a folder that is not a layer would escape the layer rules, so the check refuses it (`backend-module-files-in-a-layer`). Neither `domain/` nor `application/` imports a built-in module of Node.js or Fastify (`backend-domain-and-application-not-to-node`, `backend-domain-and-application-not-to-fastify`). Directly under `src/`, there is only `main.ts` and `server.ts`: anything else is in `modules/`, `initializers/`, `shared/` or `test/` (`backend-src-files-in-known-places`). In the core of the `logs` module, which has the four of them:
- `domain/` — the contracts the module needs from the outside: `logs.repository.ts`, the `LogsRepository`, which reads the logs of every location it watches (`getAllLogs`), reads those of one location (`getLogs`), stores logs, each at its own `location`, where they replace what was stored (`saveLogs`), and empties a location (`deleteLogs`). A location is an opaque string saying where some logs are stored, which only the implementation gives a meaning to (a file path, the address of another server). Reading gives the logs and, as self reports, the stored entries that hold no valid log; the models (`Log`, `LogCategory`) are imported from `@echo/utilities`. A `Log` carries its `location` and its `locationName`, the short name shown to the user
- `application/` — the business rules, one file per use case, named after it (`getFilteredLogs.ts`, which also saves the self reports of the repository to the `SelfReportRepository` it is given), which know nothing of HTTP
- `infra/` — `*.api.ts` reads a data source, `dto/*.dto.ts` describes what it returns (with the function converting it to a model next to it), `*.repository.ts` implements a `domain/` contract with both
- `presentation/` — `*.routes.ts`, `*.controller.ts` (the request handlers, calling into `application/`), `utils/` (pure helpers, such as the validation of the input of the handlers), and `*.schemas.ts`, the JSON schemas of the routes, derived from the zod schemas of `@echo/utilities`

`GetLogsParamsSchema` describes the query as the client sends it; `safeParseGetLogsParams` (`presentation/utils/`) validates it and turns it into what `getFilteredLogs` needs (`fromDate` and the optional `toDate` as `Date`s, `logCategories` always an array).

`logs/modules/logsNotifier/` is the submodule of `logs`, layered the same way, with the four layers. It is the optional cron that notifies the problem logs: `domain/` holds the `LastCheckDate` model and the `CheckDateRepository` contract (the date the logs were last checked at); `application/checkProblemLogsAndNotify.ts` is the use case, built on the `getFilteredLogs` of `logs` (it is therefore given two `SelfReportRepository`: the one of the logs, for the stored entries that hold no valid log, and its own); a check looks at the logs from the date of the previous check to its own, the latter left out (`toDate`), so each log is notified once, and the self reports are notified like any other log: an entry that holds no valid log is re-dated each time the logs are read, so it is notified at every check until its file is fixed, on purpose, with `application/utils/buildNotifierMessage.ts` writing the message it notifies, never longer than the size limit the use case asks the `NotifierService` for (it returns `undefined` when nothing fits, in which case nothing is sent and the use case saves a warning to its own `SelfReportRepository`, stored in `logsNotifier.jsonl`); `infra/` holds `CheckDateApi` (the last-check file), `fileCheckDate.repository.ts` implementing the contract on top of it, and `dto/lastCheckDate.dto.ts`; `presentation/logs.notifier.ts` is the Fastify plugin scheduling the use case. A cron is the entry point of the submodule the way a route is the one of `logs`, hence `presentation/`. It notifies through the `NotifierService` of `shared/services/`.

`echo_backend/src/initializers/` holds what `buildServer` registers on the Fastify app, one `register*` function per file: `registerSecurity` (cookie/JWT and CORS), `registerDocumentation` (Swagger), `registerAuthRoutes` and `registerLogsRoutes` (the routes of the API, under `apiRoutePrefix`), `registerFrontend` (the static files, under `appRoutePrefix`, and the 404 handler) and `registerLogsNotifier` (the cron), with `utils/` holding what `server.ts` shares with them or uses on its own (`normalizeToEchoError.ts`, `isOriginAllowed.ts`, `removeBasePath.ts` and `addBasePath.ts`, the `rewriteUrl` and the `Location` of the redirections of the Fastify app). They are part of the composition root, so they import the `infra/` and `presentation/` of the modules, never their `application/` (`backend-initializers-not-to-application`), and nothing but `server.ts` imports them, as nothing but `main.ts` imports `server.ts` (`backend-initializers-only-from-server`, `backend-server-only-from-entry-point`). Each one is tested in `initializers/__tests__/` on a real Fastify instance, while `src/__tests__/server.test.ts` mocks them, and only checks that `buildServer` registers each one once and that `startServer` listens on the host and port of the config (its `listen` is mocked, so no test opens a port), or exits when the config, the server or the listening fails (only `main.ts` is excluded from the coverage), through `server.inject`, with a config from `test/mocks/mockConfigs.ts` (`getMockBackConfig`, `getMockServerConfig`).

A module or a submodule may import the `domain/` and the `infra/` of any other one, whether it is another module, its parent, one of its submodules or a submodule next to it, and only its `infra/` may import the `infra/` of another one; the `application/` and the `presentation/` of a module or a submodule stay its own, with one exception: the `application/` of a submodule may import the `application/` of its parent (`logsNotifier` builds on `getFilteredLogs`). See `backend-modules-isolated`, `backend-parent-not-to-submodule-internals`, `backend-submodules-isolated` and `backend-submodule-not-to-parent-internals` in `.dependency-cruiser.mts`.

The backend `selfReport` module is how the backend reports its own diagnostics. It has `domain/` and `infra/` only (it has no route and no business rule of its own): `domain/` holds the `SelfReport` model (`date`, `message`, `level` (`'warning'` or `'error'`), `reportedFile`, and `reportedLine`, left out when the diagnostic points to no line), which is not derived from `Log`, and the `SelfReportRepository` contract the other parts of the backend report through; `infra/` holds `selfReport.repository.ts` (`createSelfReportRepository`, see below), `selfLogReport.repository.ts` (the contract on top of the `LogsRepository` of `logs`: a self report is stored as a log, at a location of `SERVER_LOGS_DIR_PATH/self_reports/<SERVER_NAME>/log`, a directory the logs are read from too, so it is read back like any other log; it leaves out the logs older than the retention when it is created, and the stored log of a self report saved again), `utils/convertSelfReportToLog.ts` (the level becomes the category, `reportedFile` the `callFile`, `reportedLine` the `callLine`, `0` when left out; the `location` and the `locationName` are those the repository is created with, the `groupName` the `selfReportsGroupName` of the config, and the `id` is made of all the rest), `SessionJobIdApi` (the session file, remembering the last `job_id` the self reports were written with: a repository takes the next one when it is created) and `dto/sessionJobId.dto.ts`. It knows neither files nor the format of a log line, which `logs/infra` alone describes. It logs what it cannot store to the `Logger` of `shared/types/logger.ts`, not to a Fastify type. A repository is created for one location, by `createSelfReportRepository` (`infra/selfReport.repository.ts`, given the `LogsRepository`, the `FilesService`, the `SelfReportsConfig`, the function picking the file name in it and a `Logger`), which makes the location from the self-reports directory and that file name, and its name from that file name without its extension, and gives a repository storing nothing when there is no `SelfReportsConfig`: whoever needs to report is given its own `SelfReportRepository` and never names a file. `logs` and `selfReport` depend on each other through contracts only: `logs` imports the `domain/` of `selfReport`, to say what it reports, and `selfReport/infra` the `domain/` of `logs`, to store.

The backend `auth` module has the four layers:
- `domain/auth.repository.ts` — the `AuthRepository` contract, the storage of the accounts: whether one exists (`hasAnyUser`), the creation of one (`createUser`, given a `NewUser`), the check of credentials (`areCredentialsValid`); `domain/signUpRefusedError.ts` — the `SignUpRefusedError` a refused sign up throws
- `application/` — `signUpFirstAdmin.ts` (`canSignUp` tells whether a user can still sign up, which the auth check asks too; `createSignUpFirstAdmin` builds the use case: only the very first user can sign up, and becomes the admin; it throws the `SignUpRefusedError` of `domain/` when another sign up is in progress or when an account already exists, the first checked and marked before any `await`, so two requests sent at the same time never both sign up, however long the storage takes to answer) and `validateCredentials.ts` (whether the credentials are those of an account, which the login handler asks)
- `infra/` — `users.db.ts` (`createUsersDb`) opens the SQLite database, `dto/user.dto.ts` describes a row of its `users` table, `authUsersDb.repository.ts` implements the contract by querying that database, hashing the passwords with bcrypt
- `presentation/` — `auth.routes.ts`, `auth.controller.ts` (the request handlers, calling the use cases, answering a 403 to a `SignUpRefusedError`, signing the JWT and setting the session cookie), `auth.schemas.ts` (the JSON schemas of the routes, derived from the zod schemas of `@echo/utilities`) and `auth.hooks.ts`, the `authPreHandler` rejecting the requests without a valid JWT. The sign up and the login are rate limited (`credentialsAttemptsLimit` of the `AuthConfig`, 5 attempts a minute per address, `@fastify/rate-limit` registered by `registerAuthRoutes` for these routes only), and checking the credentials of an unknown user compares the password to a dummy bcrypt hash, so the time of the answer does not tell which usernames exist. No other module imports it: `initializers/registerLogsRoutes.ts` hands it to the routes to protect as their `preHandler` option (`logsRoutes`), only when authentication is enabled

The frontend modules are layered like the backend ones, with imports only going `presentation → application → infra → domain` (enforced by `npm run arch:check`): there is no injection, so `application/` imports the hook or the function of `infra/` directly, where the backend goes through the contract of `domain/`.

The frontend `logs` module:
- `domain/` — the contract the module needs from the outside: `logs.repository.ts`, the `LogsRepository`, which fetches the logs (`findLogs`) and gives those matching the category and search filters, wherever they are filtered (`filterLogs`); the models (`Log`, `LogCategory`) are imported from `@echo/utilities`
- `infra/` — `useLogsRepository.ts`, the hook giving the `LogsRepository`: `findLogs` on top of the logs endpoint of the backend (it sends the request, validates the answer against `LogArraySchema` and sends the user to the auth screen on a 401), `filterLogs` on top of the Web Worker of `workers/`. The worker is one way to implement `filterLogs`, which filtering on the main thread or through the API would be others. In `workers/`: `filterWorkerMessages.ts` types the messages both sides exchange, `filterLogs.ts` wraps the worker into a promise-returning function (one request at a time, the logs sent only when they change, indexes sent back so the logs keep their identity, a rejection when the request is aborted or the worker fails), `createFilterWorkerRequestHandler.ts` is what the worker does with a request, and `filterWorker.ts`, its entry point, is the only file excluded from the coverage
- `application/` — the TanStack Query hooks: `useGetLogs` and `useFilteredLogs` (debounced, and cancelled when its filters change before it ends). There is no query key file: each query key is written in its hook
- `presentation/` — `LogsScreen`, plus its `hooks/`, `layouts/`, `components/` and `utils/` (the grouping of the logs by day, group and job, the log categories to offer, the `fromDate` query param)

The frontend `auth` module:
- `domain/` — the `AuthRepository` contract (`checkAuthentication`, `login`, `signUp`) and, in the same file, what it gives and throws: `AuthCheckResult` and `InvalidCredentialsError`
- `infra/useAuthRepository.ts` — the hook giving the `AuthRepository` on top of the auth endpoints of the backend: it sends the requests, validates the answers against `AuthTokenSchema` and turns the 401 of the backend into the `AuthCheckResult` of the auth check (`login` or `signUp`) and into the `InvalidCredentialsError` of the login, so that no layer above it reads an HTTP status or an axios error
- `application/` — the TanStack Query hooks: `useGetAuthCheck`, `usePostLogin` and `usePostSignUp`, the two mutations
- `presentation/` — `AuthScreen`, which shows one of two layouts after the auth check: `AuthFormLayout`, the credentials form of the login or of the sign up depending on its `formMode` (`useAuthForm` holds its state, submits with the mutation of that mode, alerts the outcome and redirects), or `RedirectLayout`. `hooks/useRedirectionOnAuth.ts` says where to go once authenticated

`shared/` in each workspace holds cross-module code (the config, API client setup, i18n, layouts, generic components). In the backend it also holds `types/logger.ts`, the `Logger` a part of the backend writes its errors to, and `services/`, what several modules do the same way: `files.service.ts` holds the `FilesService`, the one access of the backend's own code to the file system: nothing else imports `fs`, not even the tests, but its own (`backend-fs-only-through-files-service`); only libraries given a path by the config reach the disk on their own (`better-sqlite3`, `dotenv`, `@fastify/static`). It creates a directory (`createDirectory`), reads a file as a whole (`getFileContent`) or as lines of text (`getFileLines`), throwing a `FileDoesNotExistError` (`shared/services/fileDoesNotExistError.ts`) when it is missing, lists files (`getFilesPaths`), writes a file the same two ways, in one step, leaving no temporary file behind when it fails, one write of a file after the other, a write waiting for the previous one for 10 seconds at most (`replaceFileContent`, `replaceFileLines`), and makes a file readable by its owner only (`restrictFileAccessToOwner`). `logs/infra` catches the `FileDoesNotExistError` to read a missing log file as one with no line. It knows nothing of what the files hold nor of how they are named: `getFilesPaths` is given the function saying which files to include, so the `.jsonl` extension stays in the config. `startServer` builds it once and hands it to `loadBackConfig` (the TLS certificate and key) and to `buildServer`, which gives it to whatever reads or writes files: the log files of `logs/infra`, the last-check file, the session file of the self reports and the users database. Tests get a fake one from `test/mocks/mockFilesService.ts` (`getMockFilesService`). `notifier.service.ts` holds the `NotifierService`, how the backend sends a message to the outside: it gives the size limit of its messages (`getMessageSizeLimit`, the `telegramMessageSizeLimit` of the config) and sends one (`notify`, through the Telegram bot API, throwing when it fails). It knows nothing of what the messages say. `registerLogsNotifier` builds it with `createNotifierService(config.notification)`, only when the notifications are configured, and hands it to the logs notifier. `shared/` imports nothing of the backend but itself (`backend-shared-is-self-contained`).

A relative import never leaves its package, tests included (`no-relative-import-outside-package`): what is outside is either a package imported by its name (`@echo/utilities`, only through its barrel) or a file read when the server runs, whose path is in the config.

### Environment configuration

Env vars are parsed and validated once at startup, not read ad hoc via `process.env` elsewhere in the code:
- `parseConfig` (`echo_utilities/src/shared/config/parseConfig.ts`) parses the vars common to both frontend and backend into the `Config` (`shared/config/config.ts`): `SERVER_NAME` and `HAS_AUTHENTICATION`. Where Echo is reached is not shared: the backend reads `SERVER_URL` (`parseServerUrls` derives `apiUrl` and `appUrl` from it, `${SERVER_URL}/api` and `${SERVER_URL}/app`, its path kept), and the frontend reads it from its page (`parseAppUrls`, below). The route prefixes are `apiRoutePrefix` and `appRoutePrefix` of `echo_utilities/src/shared/config/routePrefixes.ts`.
- `echo_backend/src/shared/config/loadBackConfig.ts` builds the `BackConfig` (`shared/config/backConfig.ts`) from that, the backend-only vars and constants, and throws on startup if required vars are missing/invalid. Each variable is read by its own parser, one per file in `shared/config/utils/` (`parseHttpPort`, `parseTlsConfig`, `parseLogsNotifierConfig`, …): what a variable gives when it is unset, invalid or set to a given value is unit-tested there, while the tests of `loadBackConfig` only cover which env file is loaded, that the error of a parser is thrown, and the whole config compared to the expected one. It loads `.env.production` or `.env.development` based on `NODE_ENV`. `BackConfig` is split by what uses it: `server` (`ServerConfig`: `serverName`, URLs, `basePath` (the path of `SERVER_URL`, under which a reverse proxy serves Echo, empty at the root: `parseBasePath` refuses one starting like a route prefix), `apiRoutePrefix`, `appRoutePrefix` and `documentationRoutePrefix` (the paths the API, the frontend and the docs are served under, below `basePath`), `host`, `port` (from `HTTP_PORT`), `allowedDomain` (derived from `SERVER_URL`: its registrable domain, or its host when it is a bare name or an IP address), optional `tls`, `frontendDistDirPath`), the optional `auth` (`AuthConfig`, left out unless `HAS_AUTHENTICATION` is `true`: `sessionDurationSeconds`, `credentialsAttemptsLimit`, cookie config, `usersDbFilePath`), `logs` (`LogsConfig`: `logsDirsPaths` (`LOGS_DIR_PATH`, then `SERVER_LOGS_DIR_PATH` when the self reports are enabled), `logFileExtension`, `logFilesDirName` (the `log` directory scripts put their log files in, left out of the group names, and the one the self-reports directory ends with), and the optional `logsNotifier` (`LogsNotifierConfig`: schedule, watched categories, timezone, last-check file)), the optional `selfReports` (`SelfReportsConfig`, left out unless `SAVE_SELF_REPORTS_TO_FILE` is `true`: `retentionDays`, `selfReportsGroupName` (the group the self reports are shown under: `SERVER_NAME` made safe for a path), the self-reports directory (under `SERVER_LOGS_DIR_PATH`, which is always required, and named after that group), the names of its files, the session file) and the optional `notification` (`NotificationConfig`: `telegramChatId`, `telegramBotToken` (from `TELEGRAM_BOT_TOKEN`), `telegramBaseUrl` (a constant, the bot API without the token), `telegramMessageSizeLimit`).
- Paths and file names are part of the config too (the `data/` directory and its files, the self-reports directory, the `.jsonl` extension of the log files, `parseLogFile.jsonl`): no module builds a path from `import.meta.url` or declares a file name of its own, but `loadBackConfig`, which builds the root of the repository from it. A function takes the config of its domain (`createLogsFilesApi(config.logs, filesService)`, `createFileSessionJobIdApi(config.selfReports, filesService)`, `createNotifierService(config.notification)`), and a value needed in two places is in both configs (`serverName`). `buildServer` (`server.ts`) receives the `BackConfig` and the `FilesService` and hands them down; `startServer`, next to it, builds the `FilesService`, awaits `loadBackConfig` (async, as it reads the TLS files through that service), builds the server and starts listening, and `main.ts`, the entry point, only calls it. Tests get a config from `test/mocks/mockConfigs.ts`.
- `echo_frontend/src/shared/config/utils/parseFrontConfig.ts` builds the `FrontConfig` (`shared/config/frontConfig.ts`), which `useConfig` gives: the `Config`, plus the frontend-only `LOGS_INITIAL_DATE_DAYS_AGO` (how many days back the logs start by default) and `LOGS_MINIMAL_DATE_DAYS_AGO` (how many days back they can start at most), each read by `parseDaysAgo`, next to it. It throws if one is missing or invalid, or if the first is greater than the second. `docker-entrypoint.sh` defaults them to `2` and `14`.
- The frontend reads where it and the API are reached (`APP_URL`, `API_URL` of the `FrontConfig`) from the `<base>` of its page, which the backend adds to `index.html` and a plugin of `vite.config.ts` in dev, the tests from the `<base>` `setupTests.ts` adds: `parseAppUrls` (`shared/config/utils/`) gives the app at the base and the API next to it, on the host the user reached. `SERVER_URL` is a backend variable only.
- The frontend fetches its runtime env from a generated `env.<mode>.json` file (see `docker-entrypoint.sh`, which writes `env.production.json` from container env vars at container start — this is how the same built frontend bundle is reconfigured per deployment without rebuilding). In dev, the frontend runs on a different port than the backend (Vite on `:5173` vs the API on `:4000`), so `echo_frontend/vite.config.ts` proxies `/api` and `/documentation` to the backend — keeping the backend's `SERVER_URL` a single origin (`http://localhost:5173`) in development too.
- `HAS_AUTHENTICATION=false` disables cookie/JWT registration and the `auth` routes entirely (see `registerSecurity.ts` and `registerAuthRoutes.ts` in `echo_backend/src/initializers/`); the frontend must handle both modes.
- The optional Telegram cron (`echo_backend/src/modules/logs/modules/logsNotifier/presentation/logs.notifier.ts`) only registers if `config.logs.logsNotifier` and `config.notification` are set (the first is left out when the second is), that is if `LOGS_NOTIFIER_SCHEDULE_REGEX`, `LOGS_NOTIFIER_WATCHED_LOGS_CATEGORIES`, `TELEGRAM_CHAT_ID`, and `TELEGRAM_BOT_TOKEN` are all present (once they are, an invalid `LOGS_NOTIFIER_SCHEDULE_REGEX` or `LOGS_NOTIFIER_TIMEZONE` stops the server at startup); it tracks last-checked time in `data/last_logs_check.json`.

### Log storage and parsing

Logs are read directly from `.jsonl` files on disk (the directories of `logsDirsPaths`: `LOGS_DIR_PATH`, and `SERVER_LOGS_DIR_PATH` when the self reports are enabled), not from a database — `infra/logsFiles.api.ts` lists the log files of each directory (the files with the `logFileExtension` of the config), reads the lines of one and replaces them, through the `FilesService` of `shared/services/`; `infra/logsFiles.repository.ts` implements the `LogsRepository` of `domain/` on top of it, a location being the path of a log file: it converts each line to a log (`convertRawLogLineToLog` in `infra/dto/rawLogLine.dto.ts`), gives a warning self report for each line that holds none, and writes a log back as a line (`convertLogToRawJsonLogLine`, in `infra/dto/rawJsonLog.dto.ts`, next to the schema of a line), `saveLogs` grouping the logs by location to write each file once. A line holds neither the `id`, the `locationName` nor the `groupName` of a log: they come from the path of the file when it is read back. `getAllLogs` only reads: `getFilteredLogs` (`application/getFilteredLogs.ts`) saves those self reports to its `SelfReportRepository`, then filters the logs and sorts them from the newest to the oldest, in memory. `filterLogByCategories` / `filterLogBySearch` (in `@echo/utilities`, shared with the frontend) implement the actual filter logic so backend filtering and frontend live-filtering (`echo_frontend/src/modules/logs/infra/workers/createFilterWorkerRequestHandler.ts`, run in a Web Worker) stay in sync.

### Auth

Backend stores users in a local SQLite file at `data/users.db` (`echo_backend/src/modules/auth/infra/users.db.ts`, `better-sqlite3`) with bcrypt-hashed passwords. JWT secret is a fresh random value generated at process start (`crypto.randomBytes` in `initializers/registerSecurity.ts`) — sessions do not survive a server restart. A session lasts `sessionDurationSeconds` of the `AuthConfig` (one day), both its cookie (`maxAge`) and its JWT (`expiresIn`, set in `registerSecurity.ts`). The JWT is delivered via an httpOnly cookie whose options are derived from `SERVER_URL` at startup (`parseAllowedDomain` and `parseCookieSerializeOptions` in `shared/config/utils/`): its domain is the allowed domain (none on `localhost` or an IP address), its path the `basePath` of the `ServerConfig` (`/` when it is empty), so two instances served at two paths of one domain keep their own session, and it is `secure` only when `SERVER_URL` uses `https://`, since a browser refuses a secure cookie set over HTTP.

### Serving frontend from backend

In production the backend serves the built frontend static files (`echo_frontend/dist`) under `/app` via `@fastify/static` (`initializers/registerFrontend.ts`), with a catch-all `notFoundHandler` returning `index.html` for any `/app/*` route (SPA routing) and a 404 `EchoError` for everything else, `/application` included. API routes are mounted under `/api`.

Echo can be reached at any path behind a reverse proxy, the path of `SERVER_URL` (`basePath` of the `ServerConfig`), which the proxy may forward or strip: the Fastify app is built with a `rewriteUrl` (`removeBasePath`) taking it off the requests that carry it, so the routes stay under `/api`, `/app` and `/documentation`, and an `onSend` hook puts the `Location` of a redirection to a path of the server below it (`addBasePath`), where the browser reaches it. The frontend is built with a relative base (`./`, `vite.config.ts`; the dev server and the tests keep `/app`), and `registerFrontend` never serves `index.html` as it is: it reads it through the `FilesService` and answers it with a `<base href="<basePath>/app/">`, which its assets and `env.production.json` resolve against. Swagger UI is given the `basePath` as its `indexPrefix`, and the OpenAPI document `SERVER_URL` as its server.

### Swagger / OpenAPI

`@fastify/swagger` + `@fastify/swagger-ui` are registered in `initializers/registerDocumentation.ts` and serve live docs at `/documentation`. Keep route `schema` blocks (especially `operationId`, request/response shapes) accurate, since they drive these docs.

## Testing

Vitest is used in all three workspaces with 100% coverage thresholds enforced by `test:coverage` (see each `vitest.config.ts` for exclude lists — the entry points are excluded). Tests live in `__tests__` directories colocated with the code under test.
